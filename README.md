# HealTrip AI

مساعد صحي ذكي يساعد المستخدم في تحديد الخطوة الطبية المناسبة: طوارئ، تقييم عاجل، استشارة تخصصية، رأي ثانٍ، أو رعاية أولية. يوصي بالأطباء والمستشفيات من قاعدة بيانات حقيقية، دون تشخيص، ودون اختراع معلومات.

هذا المشروع هو تطبيق Next.js واحد يجمع الواجهة، الـ API، والـ Agent في نفس المشروع، وهو تحويل كامل من النسخة الأصلية Python (LangChain + SQL + FAISS + Gradio) مع دعم Streaming، معالجة أخطاء شاملة، ودعم إدخال المدن والدول والتخصصات بالعربي.

## لمحة سريعة

- يساعد المستخدم على تحديد مسار الرعاية الطبية المناسب
- يختار أطباء ومراكز صحية من قاعدة بيانات فعلية
- لا يقوم بتشخيص المرض أو اختراع بيانات
- يدعم العربية في المدخلات والفلترة
- يطبق نموذج بحث هجين: SQL + Matching + Semantic ranking
- يعمل كـ Next.js single app مع API routes و client state

## البنية المعمارية

```text
المتصفح (React / Next client)
  └── ChatApp: reducer + localStorage + SSE client
        │
        ├── POST /api/chat (message, language, history آخر 12 رسالة, stream)
        ▼
Route Handler (Node runtime)
  └── rate limit -> validation -> normalizeHistory
        │
        ├── stream=true: SSE (start, status, delta, reset, done, error)
        ▼
Agent (LangChain.js createAgent)
  └── middleware: callLimit -> fallback -> retry -> toolError
        │
        ├── نموذج أساسي: Gemini
        └── احتياطي: Groq
        │
        ▼
Tool Layer
  1. normalize.ts
     - يحوّل العربية والإملاءات المختلفة إلى قيم قاعدة البيانات الإنجليزية
  2. SQLite (better-sqlite3, readonly)
     - فلترة صارمة حسب المدينة، الدولة، التخصص، ونوع الجهة
  3. vector-store
     - ترتيب دلالي للمرشحين فقط باستخدام cosine similarity
  4. embeddings
     - transformers.js + multilingual-e5-base
```

## ملاحظات تصميم تقنية

### 1) لماذا Next.js بدل خدمة Python منفصلة؟

- تطبيق واحد يمنع الحاجة إلى تشغيل واجهة وخادم مستقلين
- توحيد اللغة والأنواع بين الواجهة والـ Agent
- عدم الحاجة إلى CORS أو خدمات متعددة للتتبع والمراقبة
- التحدي الرئيسي هو أن LangChain.js أقدم وأقل نضجًا من نسخته Python، خاصة في تفاصيل التغليف والأخطاء

### 2) لماذا SQL أولًا ثم الترتيب الدلالي؟

- الشروط مثل المدينة، نوع الجهة، وقدرة الطوارئ يجب أن تكون صارمة
- لا يمكن السماح لنموذج الـ embeddings باختراق قيود هذه الحقول
- أولًا تُطبق الفلاتر في SQL على القيم المتطابقة
- ثم يتم ترتيب المرشحين فقط حسب التشابه الدلالي مع وصف الحالة

### 3) لماذا استبدلنا FAISS بملف JSON؟

- عدد المزودين الحالي محدود (حوالي 25)
- مكتبة FAISS native غير مناسبة بسهولة في Node أو البيئات serverless
- يتم تصدير الـ vectors من نفس فهرس FAISS الأصلي، وهي L2-normalized
- حاصل الضرب النقطي يساوي تقريبًا cosine similarity
- عند زيادة عدد السجلات، يمكن الانتقال إلى `pgvector` أو `hnswlib` أو أي فهرس حقيقي

### 4) الـ embeddings

- يستخدم النموذج `multilingual-e5-base`
- يتم تحميله محليًا عبر `transformers.js`
- تُستخدم بادئة `query` لاستعلامات البحث كما يطلب `e5`
- هذا يجعل الأسئلة العربية تتطابق مع أوصاف الأطباء الإنجليزية بشكل دلالي
- تم حل مشكلة التأخير عبر تحميل النموذج عند إقلاع السيرفر، مع مهلة تصل إلى `EMBEDDING_TIMEOUT_MS`
- إذا فشل التحميل، يتم إرجاع نتائج مفلترة غير مرتبة مع `ranked=false` بدل فشل الطلب بالكامل
- حالة التحميل تُخزَّن في `globalThis` لأن Next يقوم ببناء bundles منفصلة لكل Route

### 5) دعم العربية في المدن والدول والتخصصات

- قاعدة البيانات باللغة الإنجليزية
- قد يمرر المستخدم أو النموذج كلمات مثل: الرياض، السعودية، أو قلب
- تم إضافة طبقة إلزامية في `normalize.ts` لتطبيع النص العربي
- تشمل المعالجة:
  - حذف التشكيل والتطويل
  - توحيد الألف والياء والتاء المربوطة
  - حذف التعريف وكلمات مثل "في" و"مدينة"
  - بناء جداول مرادفات عربية/إنجليزية لكل حقل
  - تطابق المحتوى مع الاحتواء (مثل "طبيب قلب")
  - التعامل مع الأخطاء الإملائية البسيطة

القيمة النهائية تُختار من القيم الموجودة فعليًا في قاعدة البيانات، كما أن الحقول منفصلة، لذلك يمكن أن تُحل كلمة "عمان" كدولة أو كمدينة حسب الحقل.

إذا لم يكن المكان موجودًا في القاعدة، لا يتم التخمين؛ بل يتم إرجاع قائمة المدن والدول والتخصصات المتاحة ليقترحها المستخدم على الـ Agent.

## الذاكرة وتعدد المحادثات

- كل محادثة لها معرف خاص
- الرسائل محفوظة في `localStorage`
- السيرفر لا يحتفظ بحالة محادثة
- تم التخلي عن `MemorySaver` على السيرفر لسببين أساسيين:
  - يضيع عند إعادة التشغيل
  - لا يعمل بشكل صحيح عبر نسخ متعددة من التطبيق
  - يترك حالة جزئية بعد طلب فاشل

الحدود الحالية:

- 60 رسالة لكل محادثة
- 50 محادثة كحد أقصى
- عند امتلاء التخزين، تُحذف أقدم المحادثات وتظهر تنبيه

## الـ Streaming

تم اعتماد `Server-Sent Events` بدل WebSockets لأن الاتجاه واحد فقط (من السيرفر إلى المتصفح)، وهو أسهل عبر HTTP العادي والـ proxies.

الأحداث المستخدمة:

- `start`
- `delta`
- `status`
- `reset`
- `done`
- `error`

القاعدة الأساسية:

- أي خطأ يحدث قبل البدء يُرجع كـ JSON عادي مع HTTP status مناسب
- أي فشل بعد بدء البث يُرجع كحدث `error`
- الإجابة النهائية في `done` هي الموثقة والمعتمدة
- إذا انقطع البث أو حدث خطأ، لا يتم حفظ النص الجزئي لأنه قد يكون مضللًا

## التشغيل في بيئة الإنتاج

- نبضة heartbeat كل 15 ثانية
- مهلة صمت 30 ثانية في المتصفح
- مهلة إجمالية 120 ثانية
- إلغاء الطلب من المتصفح يوقف الـ Agent على السيرفر

## ملاحظات أمنية وسلامة

- لا يوجد تشخيص أو تأكيد طبي من النظام
- يتم اقتراح مسار الرعاية فقط بناءً على البيانات والفلترة المتاحة
- لا يتم اختراع بيانات أو أطباء غير موجودين في القاعدة
- يتم التعامل بشكل صارم مع إدخالات المستخدم وفلترتها قبل أي استدعاء للـ AI
