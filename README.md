HealTrip AI

مساعد صحي ذكي يساعد المستخدم على تحديد الخطوة الطبية المناسبة (طوارئ، تقييم عاجل، استشارة تخصصية، رأي ثانٍ، رعاية أولية) ويرشح له أطباء ومستشفيات من قاعدة بيانات حقيقية، بدون تشخيص وبدون اختراع بيانات. المشروع تطبيق Next.js واحد فيه الواجهة والـ API والـ agent، وهو تحويل كامل لنسخة Python الأصلية (LangChain + SQL + FAISS + Gradio) مع إضافة streaming ومعالجة أخطاء شاملة ودعم إدخال المدن والدول والتخصصات بالعربي.

التشغيل

نفذ npm install ثم انسخ ملف .env.example إلى .env.local وضع GOOGLE_API_KEY أو GROQ_API_KEY أو الاثنين، ثم npm run dev وافتح http://localhost:3000. الأوامر الأخرى: npm test لتشغيل 81 اختبارًا، و npm run typecheck، و npm run build. أول تشغيل ينزّل نموذج الـ embeddings (حوالي 300 ميجا) في مجلد .cache/models، وهذا يحدث عند إقلاع السيرفر وليس عند أول رسالة، ولازم تنتظر سطر embeddings model ready في اللوج قبل أول تجربة حتى تكون النتائج مرتبة بالدلالة. المتغيرات الاختيارية: GEMINI_MODEL_NAME و GROQ_MODEL_NAME و DB_PATH و VECTORS_PATH و EMBEDDING_MODEL و EMBEDDING_TIMEOUT_MS و HF_CACHE_DIR و REQUEST_TIMEOUT_MS و RATE_LIMIT_PER_MIN.

الصورة العامة للـ Architecture

    المتصفح (React / Next client)
      ChatApp: reducer + localStorage + SSE client
            |
            |  POST /api/chat  (message, language, history آخر 12 رسالة، stream)
            v
    Route Handler (Node runtime)
      rate limit -> validation -> normalizeHistory
            |
            |  stream=true: SSE (start, status, delta, reset, done, error)
            v
    Agent (LangChain.js createAgent)
      middleware: callLimit -> fallback -> retry -> toolError
      نموذج أساسي Gemini، احتياطي Groq
            |
            |  tool call: find_providers
            v
    Tool
      1) normalize.ts: يحوّل العربي/الإملاء المختلف إلى قيم قاعدة البيانات الإنجليزية
      2) SQLite (better-sqlite3، قراءة فقط): فلترة صارمة بالمدينة والدولة والتخصص والنوع
      3) vector-store: ترتيب دلالي للمرشحين فقط (cosine على vectors مصدّرة من FAISS)
      4) embeddings: transformers.js (multilingual-e5-base) محمّل عند الإقلاع

الفكرة الأساسية أن السيرفر لا يحتفظ بأي حالة محادثة. المتصفح يملك المحادثات والذاكرة، ويرسل مع كل طلب آخر 12 رسالة مكتملة، والسيرفر يبني سياق الـ agent منها في كل مرة.

هيكل المجلدات

مجلد src/app فيه الصفحة والـ layout وملف globals.css (تصميم Figma الأصلي كما هو مع إضافات للرسائل والأخطاء) ومساري الـ API: api/chat و api/health. مجلد src/components فيه ChatApp (الحالة والتحكم)، و Messages (عرض الرسائل وبطاقات الأخطاء)، و icons. مجلد src/lib/chat فيه كل منطق الواجهة بدون React: types و reducer و storage و client و i18n و id، وكلها دوال نقية قابلة للاختبار. مجلد src/lib فيه منطق السيرفر: agent و tools و db و normalize و vector-store و embeddings و errors و config و request و rate-limit و prompt. ملف src/instrumentation.ts يشغّل تحميل نموذج الـ embeddings عند إقلاع السيرفر. مجلد data فيه healtrip.db و provider_vectors.json. مجلد scripts فيه export_vectors.py لإعادة بناء الـ vectors. مجلد tests فيه الاختبارات.

القرارات التقنية وأسبابها

لماذا Next.js بدل خدمة Python منفصلة. تطبيق واحد يعني نشرًا واحدًا ولغة واحدة من الواجهة إلى الـ agent، ومشاركة الأنواع (مثل شكل الأخطاء) بين الطرفين، وبدون CORS أو خدمتين تحتاجان مراقبة. الثمن أن LangChain.js أحدث وأقل نضجًا من نسخة Python، وهذا ظهر فعلًا في تفاصيل مثل تغليف الأخطاء (شرحته في قسم الأخطاء).

لماذا SQL أولًا ثم الترتيب الدلالي. شروط مثل المدينة ونوع الجهة وقدرة الطوارئ شروط صارمة لا يجوز أن يخرقها نموذج embeddings، فتُطبّق في SQL على قيم مطابقة، ثم يُرتَّب المرشحون فقط بالتشابه الدلالي مع وصف حالة المستخدم. هذا يمنع ظهور طبيب في مدينة خاطئة لمجرد أن وصفه قريب دلاليًا.

لماذا استبدلنا FAISS بملف JSON وحساب cosine داخل Node. عدد المزودين حاليًا 25 فقط، وFAISS مكتبة native لا تعمل بسهولة في Node ولا في بيئات serverless. الـ vectors مصدّرة من نفس فهرس FAISS الأصلي وكلها L2-normalized، فحاصل الضرب النقطي يساوي cosine تمامًا. عندما تصل لآلاف السجلات انتقل إلى pgvector أو hnswlib أو أي فهرس حقيقي، وواجهة vector-store صغيرة بحيث يكون الاستبدال موضعيًا. عند تغيير المزودين أعد توليد الملف بسكربت scripts/export_vectors.py (نفس النموذج ونفس بادئة passage).

الـ embeddings. نفس نموذج الفهرس الأصلي multilingual-e5-base يعمل محليًا عبر transformers.js، ويُستخدم بادئة query لاستعلامات البحث كما يتطلب e5. هذا هو سبب أن السؤال العربي يطابق وصفًا إنجليزيًا للطبيب دلاليًا. المشكلة التي ظهرت في الإنتاج: أول بحث كان ينزّل النموذج داخل الطلب فيتجاوز مهلة الـ 55 ثانية. الحل ثلاثي: تحميل النموذج عند إقلاع السيرفر، وانتظار أقصاه 8 ثوانٍ للاستعلام (EMBEDDING_TIMEOUT_MS) وبعدها يرجع البحث بنتائج مفلترة غير مرتبة ويخبر الـ agent بذلك (ranked=false) بدل أن يفشل الطلب كله، وإعادة المحاولة تلقائيًا في الطلب التالي إذا فشل التحميل. حالة التحميل مخزنة على globalThis لأن Next يبني instrumentation وكل route في bundle منفصل ولا تتشارك متغيرات الـ module.

دعم العربي في المدن والدول والتخصصات. قاعدة البيانات إنجليزية، والمستخدم (أو النموذج) قد يمرر الرياض أو السعودية أو قلب. بدل الاعتماد على أن النموذج يترجم صح كل مرة، هناك طبقة حتمية في normalize.ts: تطبيع للنص العربي (حذف التشكيل والتطويل، توحيد الألف والياء والتاء المربوطة، حذف ال التعريف وكلمات مثل في ومدينة)، ثم جداول مرادفات عربية وإنجليزية لكل حقل، ثم مطابقة بالاحتواء (طبيب قلب يطابق قلب)، ثم تسامح مع الأخطاء الإملائية البسيطة. القيمة النهائية تُختار من القيم الموجودة فعليًا في قاعدة البيانات، فلو كانت الإمارات مخزنة كـ UAE أو United Arab Emirates يعمل الاثنان. الحقول منفصلة، فكلمة عمان تُحل كدولة في حقل الدولة وكمدينة في حقل المدينة. إذا كان المكان غير موجود في القاعدة (مثل الدمام حاليًا) لا يُخمَّن شيء: تُرجع الأداة قائمة المدن والدول والتخصصات المتاحة والـ agent يقترحها على المستخدم. لإضافة مدينة أو تخصص جديد أضفه إلى الجداول في أعلى normalize.ts؛ وأي قيمة في قاعدة البيانات غير موجودة في الجداول تعمل تلقائيًا بالمطابقة الحرفية. التعليمات في الـ prompt تطلب من النموذج تمرير القيم بالإنجليزية أيضًا، لكن الضمان الفعلي هو الطبقة الحتمية.

الذاكرة وتعدد المحادثات. كل محادثة لها معرّف ورسائلها محفوظة في localStorage بنسخة schema، والسيرفر بلا حالة. بدأنا بـ MemorySaver على السيرفر ثم تركناه لثلاثة أسباب: يضيع عند إعادة التشغيل، ولا يعمل مع أكثر من instance، ويترك حالة نصف مكتملة بعد طلب فاشل. الثمن أن النموذج يرى آخر 12 رسالة فقط (كل رسالة حتى 3000 حرف)، وأن المستخدم نظريًا يستطيع تزوير تاريخ محادثته، وهذا لا يؤثر إلا على محادثته هو. إذا احتجت تدقيقًا أو ذاكرة طويلة فالبديل تخزين المحادثات في قاعدة بيانات على السيرفر. الرسائل الفاشلة أو المقاطعة لا تدخل أبدًا في السياق المرسل، ويُفرض تناوب user و assistant في المتصفح وفي السيرفر. حالة الواجهة كلها في reducer نقي (reducer.ts) مختبَر بشكل مستقل، ومنه تأتي ضمانات مثل أن الرد يصل للمحادثة التي طلبته حتى لو انتقل المستخدم لمحادثة أخرى، وأن حذف محادثة قيد التنفيذ يلغي طلبها بصمت. الرسالة التي كانت قيد الإرسال عند إغلاق الصفحة تعود كرسالة مقاطعة مع زر إعادة المحاولة. التبويبات تتزامن عبر storage event، ورقم المحادثة النشطة محفوظ في sessionStorage حتى لا تتنازع التبويبات عليه. الحدود: 60 رسالة للمحادثة الواحدة و 50 محادثة، وعند امتلاء التخزين تُحذف أقدم المحادثات ويظهر تنبيه.

الـ Streaming. اخترنا Server-Sent Events بدل WebSocket لأن الاتجاه واحد (من السيرفر للمتصفح) وهو يعمل فوق HTTP عادي ويتجاوز الـ proxies بسهولة. الأحداث: start، و delta لقطعة من الإجابة، و status مع phase=searching عند بدء استدعاء أداة البحث، و reset لمسح أي نص كُتب قبل استدعاء الأداة، و done وفيه الإجابة النهائية المعتمدة من حالة الـ graph، و error. القاعدة: أي رفض ممكن قبل البدء (JSON غير صالح، تحقق، rate limit) يرجع JSON عاديًا بكود HTTP حقيقي، وأي فشل بعد بدء البث يرجع كحدث error لأن سطر الحالة 200 أُرسل أصلًا. الإجابة النهائية في done هي المرجع، فلو تكرر نص بسبب إعادة محاولة وسط البث يُصحَّح عند الاكتمال. سياسة مهمة في سياق طبي: إذا انقطع البث أو أُوقف أو وصل خطأ في المنتصف يُحذف النص الجزئي ولا يُحفظ أبدًا، لأن نصف إجابة طبية قد يكون مضللًا؛ يظهر خطأ مع زر إعادة المحاولة. تفاصيل التشغيل: نبضة heartbeat كل 15 ثانية، ومهلة صمت 30 ثانية في المتصفح ومهلة كلية 120 ثانية، وإلغاء الطلب في المتصفح يوقف الـ agent على السيرفر ولا ندفع ثمن tokens لا يقرؤها أحد، والترويسة content-encoding none حتى لا تؤخر طبقة الضغط في Next القطع (جُرّب على سيرفر الإنتاج الحقيقي وتصل القطع تباعًا)، وتجميع تحديثات الواجهة كل 40 ملي ثانية تقريبًا حتى لا يعاد رسم الـ markdown مع كل token، والتمرير التلقائي يتبع البث فقط ما دام القارئ في أسفل الصفحة.

معالجة الأخطاء. كل خطأ في أي طبقة يتحول إلى AppError له كود ثابت وحالة HTTP وقابلية إعادة المحاولة ورسالة عربية وإنجليزية، ولا يخرج للمستخدم نص خام من مزود الخدمة. دالة classifyError تمشي على سلسلة cause لأن LangChain يغلّف أخطاء المزود في MiddlewareError ويُسقط حالة HTTP الأصلية، وهذا اكتُشف بالاختبارات. كل رسالة خطأ من جهة السيرفر تحمل سطر الطوارئ لأن المنتج صحي ولا يجوز أن يترك فشل تقني شخصًا في حالة طارئة بلا إرشاد. أداة find_providers لا ترمي أخطاء أبدًا؛ ترجع ok=false وكود الخطأ ليشرح النموذج للمستخدم أن البحث غير متاح مؤقتًا ويقدم ما يمكن من إرشاد بدون مزودين. الـ middleware بالترتيب من الخارج للداخل: حد أقصى 6 استدعاءات للنموذج في الطلب، ثم fallback إلى Groq، ثم retry مرتين بتأخير متزايد (الترتيب مقصود: كل نموذج يُعاد معه المحاولة أولًا ثم ننتقل للتالي)، ثم حماية أخطاء الأدوات. أخطاء المصادقة والحصة والمحتوى المحجوب وطول السياق وطلب غير صالح لا تُعاد محاولتها. في الواجهة تُعالج حالات: عدم وجود إنترنت، فشل الشبكة، المهلة، إيقاف المستخدم، صفحات HTML من الـ proxy، JSON تالف، الـ rate limit مع عدّاد (Retry-After)، المحتوى المحجوب (تعديل وإعادة إرسال)، تجاوز طول المحادثة (محادثة جديدة)، امتلاء المحادثة، تعذر التخزين أو تلفه، وتعطل الـ backend (مؤشر الحالة في الأعلى يعتمد على api/health).

السلامة والأمان. الـ prompt يمنع التشخيص واختراع أي بيانات مزود، ويفرض توصية بالطوارئ عند أعراض خطيرة مثل ألم الصدر، ويفصل الإرشاد الطبي عن بيانات قاعدة البيانات. الإدخال محدود (2000 حرف للرسالة و 128 كيلوبايت للطلب)، وردود الـ markdown تُعرض بدون HTML خام ولا روابط javascript. قاعدة SQLite تُفتح للقراءة فقط والاستعلامات كلها parameterized. المفاتيح تبقى في السيرفر فقط.

الاختبارات

81 اختبارًا: 59 للسيرفر و 22 للواجهة. اختبارات الـ agent تستخدم نموذجًا مبرمجًا يحاكي Gemini في البث واستدعاء الأدوات والفشل في المنتصف، فتغطي الـ middleware الحقيقي (retry و fallback و حد الاستدعاءات). اختبارات الواجهة تشغّل المكوّن الحقيقي في jsdom مع fetch مزيّف يبث أحداث SSE فعلية، وتغطي التنقل بين المحادثات والبث والأخطاء والتخزين والتبويبات. جُرّب البث أيضًا على سيرفر next start حقيقي بنموذج وهمي مؤقت (أزيل بعد التجربة). لم يُجرَّب أي شيء مع مفاتيح Gemini أو Groq الحقيقية ولا مع تنزيل نموذج الـ embeddings الفعلي لأن بيئة التطوير كانت بلا مفاتيح وبلا وصول لـ HuggingFace، فجرّب رسالة حقيقية بالعربي بعد التشغيل وتأكد أن ترتيب النتائج منطقي.

حدود معروفة وما يلزم قبل الإنتاج

الـ rate limiter في الذاكرة ويعمل لـ instance واحد، ومع عدة instances استخدم Redis. لا توجد مصادقة مستخدمين. على Vercel أو غيرها تأكد أن البث مسموح وأن المهلة القصوى للدالة (maxDuration=60) تكفي، وأن مجلد data يُضمَّن مع الدالة (مضبوط في next.config.mjs) وأن مجلد .cache/models قابل للكتابة ويستمر بين النشرات وإلا يُعاد تنزيل النموذج. عناصر الواجهة التالية موجودة من التصميم لكنها غير موصولة: صحتي والأدوية والمرفقات وبطاقة الدعم وملف Jamie Doe. اسم الجهة في الإجابة يبقى كما هو في قاعدة البيانات بالإنجليزية.
